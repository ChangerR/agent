# 自动规划与只规划

规划方式与工具权限是两个维度：`auto / only / off` 控制是否先形成计划，
`/mode auto / ask / yolo` 仍控制工具审批。规划不增加第二次执行确认，也不授予工具权限。
规划与实施默认使用当前 provider、模型及思考等级，不需要配置另一个规划模型。

## 使用

| 入口                                    | 行为                                                         |
| --------------------------------------- | ------------------------------------------------------------ |
| 普通任务                                | 默认自动识别多步骤任务，先生成结构化计划，再进入原有执行循环 |
| `/plan auto <任务>`                     | 强制先规划再执行，并保存项目的自动规划默认值                 |
| `/plan only <任务>`                     | 只规划，可以使用专用只读工具调研，不实施                     |
| `/plan execute`                         | 用户明确要求实施当前只规划的计划，不再弹一次确认             |
| `/plan pause`                           | 中断当前执行和 child，保留已取得的结果                       |
| `/plan cancel`                          | 取消当前计划和 child，保留部分结果                           |
| `/plan continue`                        | 显式继续未完成计划；要求模型先核对已有结果                   |
| `/plan revise <新方向>`                 | 中断旧执行及 child，保留有效进度，按新方向修订               |
| `/plan`                                 | 查看当前计划数据和版本                                       |
| `/plan mode`                            | TUI 选择规划方式，选择即保存到项目                           |
| `/plan auto`、`/plan only`、`/plan off` | 保存默认方式，不提交任务                                     |

`/settings` 的“规划方式”也支持一次提交即保存。配置保存在
`pluginConfig["agentlab.planning"].mode`，沿用原子写和 CAS，保留未知字段。
保存失败不改变运行模式。运行中切到 only 会中断当前实施；改变默认值不会自动启动任何任务。
已有只规划方案须用 `/plan execute` 才会转为实施，避免设置变更自动执行未完成工作。
execute 只授权当前计划，不改变 only 默认值；完成后恢复默认约束，后续实施须由新用户任务启动。

复杂度识别是默认插件中的轻量规则：多个行动词，或包含行动的较长/多行请求会先发出
一次无工具的结构化规划请求。简单问答不增加该请求。规则可能漏判或误判；模型还能通过
`plan_update` 创建计划，用户可用显式入口消除歧义。识别规则不是权限边界，可以在 preset
的规划插件中替换；only 的限制由执行器强制实施，不依赖模型遵守提示词。
只规划时给模型的工具清单也仅保留声明的专用读取及规划安全控制工具；显式 execute 后恢复实施工具。

内置 fake provider 支持只读的规划演示，例如 `/plan auto 读取并核对 README.md`；
它只演示工具与状态链路，不能用来证明真实模型或实际代码任务的能力。

## 界面

固定计划区显示目标、整体阶段、当前步骤、下一步和阻塞原因，不把每次状态变化追加进聊天。
`/plan expand`、`/plan collapse` 展开/折叠，`/plan next` 翻页，`/plan details` 查看完整结构。
窄终端仍保留当前/下一步；长文本按终端宽度截断，完整内容在详情中滚动查看。

步骤显示负责的 child、状态和审批活动；`/agents` 仍是 child 的独立详情/补充/取消入口。
详情明确标注 child 的局部计划，与父计划分开。后台子流不取得父编辑器焦点。
启动规划的命令和普通父输入共用原有 FIFO；运行中输入会排队。
暂停、取消或修订会清理尚未开始的父输入队列，避免旧方向随后重新执行；Esc 仍沿用原有中断行为。

计划先发布事件并让终端完成该帧刷新，再进入实施请求；工具批次中的计划变更也有同样的交接点。

## 执行约束与完成依据

- only 只允许当前插件声明的 `read_file / glob / grep` 专用工具，且必须具有完整、纯读取的分析结果。
  deny、敏感目标、越界检查和正常审批仍然生效。
- only 不允许 Bash、PowerShell、Shell 别名、未知/MCP 工具或 `agent_spawn / agent_send`。
  直接 SDK 子任务入口同样检查限制；不能让已有可写 child 代执行。
  `agent_status / agent_wait / agent_cancel` 只是观察/停止已有工作，不启动工作。
- 约束在唯一 `ToolExecutor` 中执行，并在异步审批之后、实际调用前重验。
  reviewer 返回 allow 或使用 yolo 都不能绕过它。未改变 #30 的正常专用只读权限行为。
- 每个计划和步骤都有稳定 ID。模型更新必须携带最新 `revision`；用户操作或 child 状态变化后，
  旧响应不能覆盖新计划。模型响应期间计划变化，该响应中的工具调用会返回 `plan_stale`。
- 父步骤先设为 running，再执行工具。完成需非空的具体 `evidence`，至少一次成功执行或已结束的 child，
  且相关执行已经结算。工具失败会清除该步骤的成功依据并显示阻塞；没有自动“全部完成”。
  成功工具记录是最低门槛，不能替代人对证据内容的审阅，也不能自动证明整个功能正确。
- `agent_spawn.planStepId` 显式绑定父步骤；省略时绑定父当前步骤。不同 child 可以绑定不同步骤。
  父当前步骤有独立 `activeStepId`，后台 child 不会抢占父工具的执行依据。
  spawn 成功仅表示 queued/running，不能完成步骤；必须等待 child 终态并明确核对结果。
- child 失败、取消、限额、中断会阻塞对应步骤；审批显示等待原因。
  追加消息及新 run 会重新打开该步骤，旧 run 的迟到事件不会覆盖新 run。
  显式 send 可以继续已中断的 child 局部计划，普通迟到事件不能重新启动它。
- 修订保留已完成步骤和仍有活动 child 的步骤。已结束但失败/取消的未完成步骤可以在修订中移除，
  child 历史仍保留在原 supervisor 中；需要重做时也可通过 send 在原绑定上启动新 run。

## 持久化、恢复与扩展

计划快照复用现有 session 文件、schema 校验、串行原子保存和版本冲突处理。
状态变化会保存安全历史快照；恢复过程不发新模型请求，不重放工具或旧审批。
运行中的计划/child 标记为 interrupted，继续必须由用户显式发起。
已成功完成的步骤与依据保留；未完成步骤的运行时成功标记不跨重启复用，应重新核对结果。

`src/core/plan.ts` 只保存状态、验证转换和实施限制，不负责调度。
`src/builtin/planning/` 提供默认识别/规划策略、工具、命令、设置和 TUI。
`AgentLoop` 复用当前 provider 和现有事件/usage 路径，`AgentSupervisor` 复用原有取消、审批、
并发限制、消息和结果回传；没有第二套 scheduler。
SDK 可读取 `agent.loop.plan.snapshot`、订阅 `plan_changed`；自定义 preset 可以通过
`RuntimeServices.configurePlanning` 安装策略。插件仍是受信任的进程内代码，并非 OS 沙箱。
