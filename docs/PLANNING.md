# 自动规划与执行

直接描述任务即可。每个新任务默认先使用当前模型、完整对话和项目上下文做一次结构化规划判断：
简单问答或单个明确操作返回 `null`，随后正常处理；项目检查、代码审查、优化建议、问题调查和
多步骤实施返回计划。宿主先发布计划并把首步设为进行中，再进入执行、验证和步骤更新。
这增加一次规划请求，但不再依赖执行模型自愿调用 `plan_update` 才能显示计划。
用户不需要先选择模式或使用带参数命令，也不需要在每一步之后说“继续”。

独立的仓库审查先读取共享约定，再将两个互不依赖的方向绑定到父步骤并启动 child，
两次启动后再等待和核对结果；依赖前置结论的步骤仍按顺序执行。简单任务不强制委派。
沿用全树 Supervisor 限额，缺省最多两个 child，用户显式设置继续生效。
规划器对仅授权审查/建议的任务返回 `readOnly: true`，宿主在执行门强制纯读取，
并传递给后代；模型显式传 `readOnly: false` 也不能扩大父任务范围，不能借已有可写 child 绕过。
这是普通只读审查，与 `only`（只产出方案、不启动 child）分别处理。

计划未完成时，如果模型只返回方案或进度汇报，执行循环会按规划插件的策略提醒它接着做。
继续使用同一次运行、原用户授权和剩余轮数预算。相同执行进度最多提醒一次，避免反复空答；
成功执行实际工具或完成步骤后才允许再次提醒，单纯查询计划或调整状态不算执行进度。
需要用户信息、权限或外部条件时，模型应标记具体阻塞并说明；已阻塞、暂停、取消、只规划、
输出截断或预算耗尽时不会自动催促实施。审批拒绝也不会因自动推进获得新的授权。

规划方式与工具权限是两个维度：`auto / only / off` 控制是否先形成计划，
`/mode auto / ask / yolo` 仍控制工具审批。规划不增加第二次执行确认，也不授予工具权限。
规划与实施默认使用当前 provider、模型及思考等级，不需要配置另一个规划模型。

## 可选控制入口

以下入口用于主动限制、查看或调整工作，不是日常任务的前置配置。

输入 `/plan` 即打开面板，不接受参数或任务文本；任务始终在普通输入框提交。
面板前三项是自动规划、只规划、关闭自动规划，选择即保存到项目；Esc 取消不写入。
已有计划时，面板另提供查看、执行、继续、修订、暂停与取消操作。
修订使用单独输入框，提交后才中断旧工作并应用方向；取消输入不改变计划。
脚本宿主通过 `dispatchCommand('/plan', { interact })` 选择操作，没有交互回调时返回面板描述。
`/settings` 的“规划方式”也支持一次提交即保存。配置保存在
`pluginConfig["agentlab.planning"].mode`，沿用原子写和 CAS，保留未知字段。
保存失败不改变运行模式。运行中切到 only 会中断当前实施；改变默认值不会自动启动任何任务。
已有只规划方案须在 `/plan` 面板选择“执行当前计划” 才会转为实施，避免设置变更自动执行未完成工作。
execute 只授权当前计划，不改变 only 默认值；完成后恢复默认约束，后续实施须由新用户任务启动。

默认路径不根据行动词数量或文本长度判断复杂度。独立规划请求使用完整对话和项目上下文，
计划创建后由正常执行循环读取项目、修订步骤、执行和验证。规划输出不合法时明确报错，
不会静默跳过计划开始实施。规划策略可以通过 preset 替换；
only 的限制由执行器强制实施，不依赖模型遵守提示词。
只规划时给模型的工具清单也仅保留声明的专用读取及规划安全控制工具；显式 execute 后恢复实施工具。

内置 fake provider 支持只读的规划演示，例如选择自动规划后，在普通输入框提交“读取并核对 README.md”；
它只演示工具与状态链路，不能用来证明真实模型或实际代码任务的能力。

## 界面

固定计划区默认只显示一行摘要：阶段、完成数和具体步骤，优先显示阻塞原因；不把每次状态变化追加进聊天。
`Ctrl+T` 展开/收起，展开后 `Alt+↑/↓` 浏览完整步骤、依据、原因和 child 活动，无需输入命令。
这些按键不改变父编辑器或审批焦点，普通方向键和 Enter 保留原功能。
窄屏按实际终端字符宽度截断摘要，展开内容按宽度换行并限制高度，避免长目标或原因挤走输入。
新计划、切换或恢复会话重新收起；同一计划的普通状态更新不重置用户的浏览状态。
计划展开和浏览使用上述快捷键；详情也可从 `/plan` 面板打开。
产品参考和精确源码链接见 [官方交互参考](PLAN-INTERACTION-REFERENCES.md)。

步骤显示负责的 child、状态和审批活动；`/agents` 仍是 child 的独立详情/补充/取消入口。
详情明确标注 child 的局部计划，与父计划分开。后台子流不取得父编辑器焦点。
启动规划的命令和普通父输入共用原有 FIFO；运行中输入会排队。
暂停、取消或修订会清理尚未开始的父输入队列，避免旧方向随后重新执行；Esc 仍沿用原有中断行为。

计划先发布事件并让终端完成该帧刷新，再进入实施请求；工具批次中的计划变更也有同样的交接点。

## 执行约束与完成依据

- only 只允许当前插件声明的 `read_file / glob / grep` 专用工具，且必须具有完整、纯读取的分析结果。
  deny、敏感目标、越界检查和正常审批仍然生效。
- only 不允许 Bash、PowerShell、Shell 别名、未知/MCP 工具或 `agent_spawn / agent_send`。
  直接 SDK 子任务入口同样检查限制；不能让已有可写 child 代执行。
  `agent_status / agent_wait / agent_cancel` 只是观察/停止已有工作，不启动工作。
- 约束在唯一 `ToolExecutor` 中执行，并在异步审批之后、实际调用前重验。
  reviewer 返回 allow 或使用 yolo 都不能绕过它。未改变 #30 的正常专用只读权限行为。
- 每个计划和步骤都有稳定 ID。模型更新必须携带最新 `revision`；用户操作或 child 状态变化后，
  旧更新不能覆盖新计划。授权、暂停、修订等执行边界变化后，旧响应中的工具调用会返回 `plan_stale`。
  child 的普通活动文字只更新展示；生命周期进度更新 CAS 版本，不使父在途响应整体失效。
- 父步骤先设为 running，再执行工具。完成需非空的具体 `evidence`，至少一次成功执行或已结束的 child，
  且相关执行已经结算。工具失败会清除该步骤的成功依据并显示阻塞；没有自动“全部完成”。
  成功工具记录是最低门槛，不能替代人对证据内容的审阅，也不能自动证明整个功能正确。
- 完成步骤时可在同一个 `plan_update` 中传 `nextStepId`，原子完成当前步骤并启动指定的 pending 步骤。
  使用同一 revision 校验，只发布一次变更；目标无效、旧版本、缺失证据、执行或 child 未结算时，两步均不改变。
  不自动恢复 blocked 步骤，不越过 only、暂停或明确拒绝。更新结果只返回 id/revision/phase/activeStepId，
  完整最新计划在下一次请求尾部的 `runtime_plan` 中提供，`plan_status` 仍可按需读取完整状态；不改写旧消息。
- 只读任务中，未执行且分析不完整的命令（包括未知程序接 PowerShell 格式化管道）仍被拒绝，
  但可保留当前步骤和已有读取证据，让后续专用读取正常审批。已识别写入、网络、危险、敏感/项目外目标、
  真正执行失败及明确权限拒绝仍保留阻塞语义。不能把错误文字或一次被拒调用作为成功执行证据。
- `agent_spawn.planStepId` 显式绑定父步骤；省略时绑定父当前步骤。不同 child 可以绑定不同步骤。
  父当前步骤有独立 `activeStepId`，后台 child 不会抢占父工具的执行依据。
  spawn 成功仅表示 queued/running，不能完成步骤；必须等待 child 终态并明确核对结果。
- child 失败、取消、限额、中断会阻塞对应步骤；审批显示等待原因。
  同一步中其余 child 的进度不会清除已发生的失败。
  追加消息及新 run 会重新打开该步骤，旧 run 的迟到事件不会覆盖新 run。
  显式 send 可以继续已中断的 child 局部计划，普通迟到事件不能重新启动它。
- 权限拒绝在计划内保留原因和来源，child 拒绝同时约束根计划及兄弟的新执行。
  原本没有计划时记录一项具体被拒绝操作，仍复用相同的状态和持久化路径；不会因缺少父计划漏掉 child 的本地拒绝。
  模型不能通过改回 running、重复调用或换 child 自动重试；暂停、状态查询和取消继续可用。
  用户通过已有继续/修订入口显式恢复前，拒绝约束不会因中断或会话恢复消失；继续也不替代正常工具审批。
- 修订保留已完成步骤和仍有活动 child 的步骤。已结束但失败/取消的未完成步骤可以在修订中移除，
  child 历史仍保留在原 supervisor 中；需要重做时也可通过 send 在原绑定上启动新 run。
- 收窄范围可以删除已结算的当前未完成步骤，并清除旧的 `activeStepId`；新步骤仍需显式启动。
  在途工具所绑定的步骤不能删除或改名。保留相同 ID/标题时保留有效进度，改名后的未完成步骤
  清除旧成功依据，不能把旧工作的结果用于完成新工作；校验失败不改变计划或依据。

## 持久化、恢复与扩展

计划快照复用现有 session 文件、schema 校验、串行原子保存和版本冲突处理。
状态变化会保存安全历史快照；恢复过程不发新模型请求，不重放工具或旧审批。
运行中的计划/child 标记为 interrupted，继续必须由用户显式发起。
已成功完成的步骤与依据保留；未完成步骤的运行时成功标记不跨重启复用，应重新核对结果。

`src/core/plan.ts` 只保存状态、验证转换和实施限制，不负责调度。
`src/builtin/planning/` 提供默认识别/规划策略、工具、命令、设置和 TUI。
`AgentLoop` 复用当前 provider 和现有事件/usage 路径，`AgentSupervisor` 复用原有取消、审批、
并发限制、消息和结果回传；没有第二套 scheduler。
SDK 可读取 `agent.loop.plan.snapshot`、订阅 `plan_changed`；自定义 preset 可以通过
`RuntimeServices.configurePlanning` 安装策略，`PlanningStrategy.continuation` 提供结束前的继续提示，
loop 负责只在有效执行状态下调用、限制空转并保留预算和中断。插件仍是受信任的进程内代码，并非 OS 沙箱。

`PlanningStrategy.turnBudget` 可在请求前追加预算提醒，并声明当前请求只汇报、不执行工具。
默认插件对执行中的只读调研与 `only` 规划阶段启用：预算过半及剩余五轮时提醒收窄范围、同步计划，
最后一轮（总预算至少两轮）预留为无工具汇报，说明已有发现和未验证项。
`only` 的汇报说明待实施方案、验证方式与假设，不声称实施已完成，不解除只规划约束。
只读执行的同一步骤累计成功执行至少 6 次和 12 次工具后，各追加一次进度核对提醒；
单轮内按计划 ID、步骤 ID 与检查点去重，不增加模型请求、不反复追加完整计划。
这些计数来自执行器已结算的真实结果，控制工具与失败结果不增加计数，恢复会话不继承成功记录。
计数只是提醒时机，不构成完成证明；是否完成仍由既有 evidence 与步骤约束校验。
提醒只追加到消息尾部，system、工具定义和历史前缀保持稳定；汇报请求通过规范化的
`toolChoice: 'none'` 禁用新工具调用，provider 只翻译为对应协议的 `tool_choice`。
DeepSeek 的 Anthropic 兼容接口明确支持此选项，见[官方兼容说明](https://api-docs.deepseek.com/guides/anthropic_api/)；
不通过删除工具定义或改写已有工具历史实现汇报。服务端是否复用缓存仍由厂商决定。
即使 provider 仍返回工具调用，loop 也只回填未执行结果，保留合法历史并停止；空答有明确兜底提示。
汇报仍计入原 `maxTurns`，不触发 continuation，不将未完成计划标成 completed。
普通实施任务、子任务及未实现此钩子的策略保持原有预算行为。
